A take is a folder under the output root with one file per stream and a
`manifest.json` that describes them. The manifest is written when the take is
created, rewritten on every state change, served live by `GET /takes/{id}`
while recording, and pushed as a `take` event each time it changes. It is
the only thing a client needs to read.

## Two rules

**Take ids are the handle; paths are the answer.** A client holds
`20260912T040433-fd9q` and asks Rheocles what that means. It never
assembles a path from a naming convention.

**Every path is relative.** The take folder (`destination`) is relative to
the output root, which `GET /` reports as the one absolute path in the API;
each stream's `path` is relative to the take folder. A client that stores
them as given survives the root moving, the volume being renamed, and the
take being copied to another machine; a client that stored absolutes did
not.

## Written atomically

The manifest is rewritten as a temp file in the take folder and then renamed
over the old one, on every state change: create, start, each join, leave
and marker, stop, and any failure. At any instant on
disk it is either the previous complete version or the next. There is no
moment at which a reader can see half a manifest.

That is what makes a crash survivable rather than recoverable: a process that
dies mid-take leaves fragmented MOVs that play to their last fragment and a
manifest that says `recording`, with every stream's `started`. Nothing has
to be reconstructed.

## The states

| `state` | meaning |
|---|---|
| `created` | paths reserved, manifest written, nothing recording |
| `recording` | the cue has happened; writers are live |
| `complete` | stopped cleanly; every file finalised |
| `incomplete` | stopped by a failure, superseded before it started, or cut short by the daemon going away; `reason` says which; every file is playable as far as it got |

The single file, when there is one, has a state of its own — `combined.state`,
[below](#combined) — and it never feeds back into `state`. A take whose
combine failed is still `complete`.

A daemon asked to quit — `SIGINT` or `SIGTERM` — finalises the active take
first: every writer closes and the manifest reads `incomplete`, reason
`daemon stopped`, so a cleanly stopped daemon never leaves a take saying
`recording`. A manifest that *does* still say `recording` when the daemon
next launches is from one that died without finalising — a crash, a
`kill -9`, a power cut — and is rewritten `incomplete`, reason `daemon died`,
on that launch. A recovered take is never served as the live take; `stop` or
a marker against it is a `409`.

A take **created but never started recorded nothing**, so it is not kept.
Superseded by the next create, or still `created` when the daemon stops or on
the next launch, its manifest-only folder is **removed** rather than left
behind — a paired recorder that re-creates its take on every arm change would
otherwise strew an empty folder per change. The final `take` event reads
`incomplete` (reason `superseded before start`, `daemon stopped before start`,
or `daemon died`) with `removed: true`, so a client drops it from its list, and
`GET /takes/{id}` then answers `404`. A folder holding any recorded file is
never removed.

The shape is pinned by `docs/openapi.yaml` (`Manifest`, `ManifestStream`)
and rendered field by field on the [reference](/docs/api/reference#takes).
Where this page and the reference disagree, the reference is right.

### The take

| field | is |
|---|---|
| `id` | the handle: the UTC create time to the second and a short random suffix |
| `name` | what you called it, if you did |
| `state` | one of the four above |
| `reason` | only when `incomplete`: what happened, listing every stream's error |
| `created` `started` `stopped` | **UTC** ISO 8601 with milliseconds; `started` is the cue. The one place the manifest is UTC and the files are local: across midnight, this is the authority |
| `outputRoot` | absolute, **as it was at create** — so a moved root does not orphan the take |
| `destination` | the take folder, relative to the output root |
| `version` | the Rheocles that wrote it |
| `machine` | `hostname` and `machineId` (the kernel host UUID), for two-box setups |
| `settings` | `codec` and `expectedDuration` in effect |
| `combined` | only when the take was created with `combine`, or one was run after the fact: the single file's `path`, `state` and, when failed, `reason` — [below](#combined) |

### Each stream

| field | is |
|---|---|
| `id` `kind` `name` `model` | the three identity fields plus kind; all recorded because ids change across reconnects |
| `path` | relative to the take folder |
| `codec` | `hevc`, `prores`, or `pcm_s24le` |
| `format` | `video` or `audio`, as recorded — the device's `active` format at the cue |
| `started` `stopped` | this stream's own host times — a late joiner's `started` is later than the take's |
| `timecode` | `HH:MM:SS:FF`, the **local** time of day of the first written frame, as stamped into the file |
| `timeReference` | audio only: the BWF `TimeReference`, samples since local midnight at the first sample |
| `framesWritten` | frames (video) or samples (audio) actually written |
| `framesDropped` | video, absent when zero: frames the encoder was not ready for under load |
| `drift` | seconds: delivered frames × nominal frame duration versus the timeline they span — **absent for displays and windows**, whose cadence is content-driven; absent until measured, never zero by default |
| `events[]` | `{ t, type }`: `join` and `leave`, `t` in seconds from the cue to the millisecond |
| `error` | only when something went wrong for this stream — `not armed at the cue`, a write failure |

### `markers[]`

`{ t, label }`, `t` in seconds from the cue. Rheocles stamps `t`; the client
owns `label`, and Rheocles never interprets it. See [Markers](/docs/markers).

### `combined`

Present only when the take asked for a single file — `combine: true` on
create, `settings.combine` on by default, or `POST /takes/{id}/combine`
afterwards. See [One file, when there is one
camera](/docs/recording-a-take#one-file-when-there-is-one-camera) for what
the file is.

| field | is |
|---|---|
| `path` | `combined.mov`, relative to the take folder |
| `state` | `pending`, `complete` or `failed` |
| `reason` | only when `failed`: what went wrong — an export error, or `daemon died` |

| `combined.state` | meaning |
|---|---|
| `pending` | the mux is running, or is queued behind stop; the file may already exist on disk and is not yet whole |
| `complete` | the single file is final: the one video track, its `tmcd`, and every audio stream as its own track |
| `failed` | the mux did not finish; `reason` says why; the per-stream files are untouched and the take's own `state` is what it was |

The block is written `pending` at create (or when the after-the-fact call
is made) and flips to `complete` or `failed` when the export finishes, which
is after `stopped`; a `take` event carries the manifest each time. A
`pending` that outlives the daemon — it died mid-mux — is rewritten
`failed`, reason `daemon died`, on the next launch, and the half-written
file is removed.

## Reading it

```sh
curl -s -H "$H" localhost:7447/takes/20260912T040433-fd9q \
  | jq '.streams[] | {path, timecode, framesWritten, drift}'
```

```json title="GET /takes — recent takes, newest first"
[ { "id": "20260912T040433-fd9q", "name": "Episode 12", "state": "complete",
    "created": "2026-09-12T04:04:33.235Z",
    "destination": "takes/2026-09-11/210433-episode-12", "streams": 5,
    "combined": { "path": "combined.mov", "state": "complete" } } ]
```

`GET /takes/{id}` serves the manifest live while recording and from disk
afterwards. `GET /takes` lists the active take, then this process's finished
ones, then whatever the output root holds, up to fifty. A summary carries
the take's `combined` block when it has one — `path`, `state`, `reason` —
so a list can show the single-file line without fetching each manifest; a
take that never asked for one has no `combined` key at all. The file is the
source; the API is a reader.

The same manifest arrives as a `take` event on `/events` and the WebSocket
on every state change, so a client that is listening never has to poll for
`state`. While recording, a `levels` event about four times a second
carries each stream's `framesWritten`, `drift` and — for audio — `levelDb`,
the peak dBFS since the last one: the meters, and a live drift readout.
